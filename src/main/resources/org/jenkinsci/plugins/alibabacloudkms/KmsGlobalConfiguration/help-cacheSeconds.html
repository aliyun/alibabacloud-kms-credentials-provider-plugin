How long, in seconds, a retrieved secret value is cached before the next read goes back to KMS. This applies to every credential type, including a managed username/password pair. Set it to 0 to never cache: every read is then served live from KMS. The value can also come from the ALIBABA_CLOUD_KMS_CACHE_SECONDS environment variable or the jenkins.alibabacloud-kms.cacheSeconds system property, which take precedence over this field — a value typed here has no effect while either is set.

A rotated secret is picked up sooner than this lifetime regardless of its value, because the credential object is keyed on the secret's updateTime: a rotation builds a fresh credential that reads live rather than reusing a cached value. The lifetime only bounds how long repeated reads of an unchanged secret are served from cache — which is what keeps credential dropdowns cheap, since Jenkins resolves the value while rendering every entry. At 0 each of those renders costs a KMS call.

Credential discovery has its own fixed 30-second window, which this setting does not change. A lookup after that window reloads the list in the background and returns the previous result meanwhile, so new secrets, deletions and mapping-tag changes appear on the next lookup rather than blocking the one that triggers them. Only the very first lookup for a given configuration waits on KMS. A controller that stops looking credentials up altogether drops the entry after five minutes, and its next lookup blocks on a fresh one.

A failed read of a managed secret is remembered for 30 seconds before it is retried, even at a 0 lifetime, so an outage costs one timeout per secret rather than one per dropdown entry or binding.

Reload cache discards both the cached values and the discovery result.
